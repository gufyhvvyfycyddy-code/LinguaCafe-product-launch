# User Validation — 10 → 50 → 100

## 为什么先做用户验证

发布平台的曝光不等于真实用户。

社区案例：

- 2026 年一位 SaaS 作者在 Product Hunt 上线后只有少量访问、没有真实用户：
  https://www.reddit.com/r/SaaS/comments/1ulc06r/
- Hacker News 的 first-100-users 复盘强调目标社区、主动接触和持续反馈：
  https://news.ycombinator.com/item?id=44170619
- Consumer SaaS 讨论中，直接访谈、持续内容、邮件更新、快速响应都被反复提到：
  https://news.ycombinator.com/item?id=40996370
- 一个 10 个付费客户的复盘使用 HN、Reddit、冷联系获得早期用户，然后集中处理高频反馈：
  https://news.ycombinator.com/item?id=33793486

这些都是案例，不是保证有效的公式。

## 第一轮：10 个深度用户

必须真用完整主流程：

1. 登录；
2. 导入/打开真实文章；
3. 查词或标记不认识内容；
4. 确认至少一个具体词义；
5. 完成阅读；
6. 回来复习；
7. 另一天再次使用。

记录：
- 在哪一步停住；
- 哪些术语看不懂；
- 哪里比原来的方法更慢；
- 找不到什么；
- 为什么第二天愿意/不愿意回来。

## 第二轮：30–50 个封闭测试用户

只记录能回答产品问题的数据：

- 注册 → 第一篇文章；
- 第一篇文章 → 第一个确认词义；
- 第一个词义 → 第一次正式复习；
- time-to-first-value；
- D1；
- D7；
- 每周阅读次数；
- 真正完成复习的人数；
- 每个活跃用户的客服问题数量。

## 第三轮：约 100 个公开测试用户

前两轮证明用户能理解并重复主流程以后再扩大。

增加：
- 稳定性；
- 服务器负载；
- 恢复演练；
- 客服负担；
- 不同渠道的 activation；
- 不同渠道的 D7。

## 第一成功指标

用户因为 LinguaCafe 能更省事地处理真实阅读中的词汇，而再次回来阅读。

GitHub Star、下载量、页面浏览量只能作为辅助数据。
